# Contract Delta — `openapi.yaml`

The OpenAPI spec is auto-generated by `make openapi` from struct tags on the HTTP DTOs. The deltas below describe what the regen will produce after the DTO changes in `internal/adapter/inbound/http/dto.go`.

## Affected response schemas

### `http.CreateDocumentResponse`

```diff
 http.CreateDocumentResponse:
   properties:
     externalID:
       type: string
     id:
       type: string
+    imageHeight:
+      type: integer
+    imageWidth:
+      type: integer
     mimeType:
       type: string
     reused:
       type: boolean
     size:
       type: integer
   required:
     - id
     - externalID
     - mimeType
     - size
     - reused
   type: object
```

`imageWidth` / `imageHeight` are NOT in `required` — they're `*int` with `omitempty` on the Go side, so `apispec` emits them as optional. Generated TypeScript: `imageWidth?: number`.

This response is reused by `POST /internal/file` (create) and `POST /internal/file/copy` (copy).

## Endpoints affected

- `POST /internal/file` — Create response gains optional `imageWidth` / `imageHeight`.
- `POST /internal/file/copy` — Copy response gains them (shares `CreateDocumentResponse` schema).
- `PUT /internal/file/{id}/content` — Replace response gains them.
- `PATCH /internal/file/{id}` — Update response gains them.

Endpoints unchanged in shape:
- `GET /rest/storage/document/{id}` (public file serve — bytes only, no JSON metadata)
- `GET /internal/file/{id}/content` (bytes only)
- `GET /internal/file/{id}/meta` (out of scope for this PR per spec; file-metadata GET shape stays as-is)
- `DELETE /internal/file/{id}`
- `POST /internal/file/copy` request schema (only the response gains the fields)

## Behavior contract for clients

When a client calls one of the four metadata-returning endpoints with an `image/*` content (raster, SVG, or GIF), the response body now includes `imageWidth` and `imageHeight` representing the **post-rotation** pixel dimensions a renderer would draw. For non-image uploads (PDF, video, document, archive), the fields are absent. For image uploads where libvips couldn't parse the bytes, the fields are absent (the row carries `{ "_decodeFailed": true }` internally; the wire just sees the absence).

For the `POST /internal/file` happy path, dims are computed by `Process` at upload time. For Copy/PATCH on legacy rows whose `content_metadata` is empty, dims are computed lazily during the request via a header-only decode of the stored bytes (microseconds for any file size) and persisted to the row.

When the lazy-backfill itself fails (e.g., `Storage.Read` transient error), the underlying request still returns its normal 2xx response with the dim fields absent — backfill failures never cascade into a 5xx for an unrelated PATCH/Copy/Create-dedup operation.

## OpenAPI generation

```bash
make openapi
```

CI verifies the regenerated file matches what's checked in (`openapi is stale` job). The PR must include the regenerated `openapi.yaml`.

## Reserved JSON keys in `content_metadata`

While not part of the wire contract directly, callers inspecting the `file` table should know:

- `imageWidth`, `imageHeight` — the canonical fields surfaced on responses.
- `_decodeFailed` — internal sentinel (leading underscore convention) for unreadable image bytes. Consumers should treat any leading-underscore key as internal and not rely on its presence.
- Future per-content-type fields (`videoDuration`, `pageCount`, etc.) will land at the top level when the corresponding producers are implemented.
